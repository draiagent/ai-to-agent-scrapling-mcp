# 🚀 AI to Agent Web Intelligence MCP
## 從「幫我找資料」，走向「交付可追溯的企業情報」

企業使用 AI，經常遇到一個問題：文章寫得很漂亮，資料卻不知道從哪裡來；摘要看起來很完整，真正要決策時，還得重新查一次。

比較供應商、蒐集研究文獻、追蹤競品活動，每項工作都涉及找網頁、讀內容、整理欄位與比對差異。當這些步驟分散在人員與工具之間，時間就消耗在重複搬運資料。

**AI to Agent Web Intelligence MCP** 希望建立一套清楚的工作方法：讓 Agent 取得外部資料，再將資料整理成有來源、有結構、可驗證、可交接的成果。

專案名稱統一為 `ai-to-agent-web-intelligence-mcp`。圖卡上的「AI to Agent × Scrapling MCP」介紹底層工具搭配；整個專案的價值，則是企業情報與知識工作流。

### 🧠 三個角色，一次看懂

👁️ **Scrapling 是眼睛**：負責擷取網頁內容，依頁面需求選擇適合的資料取得方式。

🔌 **MCP 是工具接口**：讓 Agent 呼叫工具、取得結果，串起任務與執行能力。

📚 **Knowledge Pipeline 是情報整理流程**：統一欄位、保留證據、比較差異，再形成報告或知識筆記。

我們用 **Web Intelligence Brain** 比喻這套上層架構。它不是 Scrapling 官方產品，也不是已完成的自訂伺服器。重點是讓資料支持下一步行動。

### 🛠️ 如何使用？

**第一步：閱讀圖卡與 README。** 先確定工作問題，例如比較原料報價、整理研究資料或分析會員活動。

**第二步：安裝並連接官方 MCP。** 依指南建立 Python 環境，以 `scrapling[ai]` 安裝套件，再用 `scrapling install` 安裝瀏覽器依賴。依客戶端版本完成 MCP 設定與驗收。

**第三步：交代四個要素。** 提供目的、來源、欄位與交付格式。比較哪些產品？允許讀取哪些網址？需要價格還是規格？最後要表格還是研究筆記？

**第四步：核對成果再擴大。** 先完成一個網址、一次任務，確認資料正確、缺漏有標示、來源能回查，再增加網站與工作量。

以下三個案例皆為教學模擬，並非已完成的真實研究或報價結果。

### 📦 模擬案例一：原料供應商比較

採購同仁要比較三家乳清蛋白原料供應商，但包裝、規格與報價條件不同，不能只看表面價格。

**關鍵提示詞：**

> 請讀取我提供的三個供應商產品網址，整理品名、蛋白質含量、包裝重量、價格、幣別、最低訂購量與報價日期。每筆資料保留來源及原文依據。缺漏寫「未提供」，不同規格先不要排名，最後列出需要詢價的問題。

**模擬產出：** 一份供應商比較表，以及待確認清單。A 廠公開包裝重量，但價格需詢問；B 廠有價格，卻缺最低訂購量；C 廠規格不同，暫時不能直接比較。

Agent 應指出「目前資料不足以判定誰最便宜」，再整理各家需要補問的資訊。採購人員可以帶著明確問題詢價，減少來回確認，也避免將不同規格放在一起排名。

### 🔬 模擬案例二：CGM 研究文獻整理

講師準備連續血糖監測教材，需要看清楚研究對象、設計與證據限制。

**關鍵提示詞：**

> 請根據我提供的五篇公開研究網址，整理題名、年份、研究設計、受試者特徵、樣本數、主要結果與限制。區分原文結論與整理推論；只能讀到摘要時註記。最後提出三個課堂討論問題，不延伸為個人治療建議。

**模擬產出：** 一份文獻證據表與教學提綱。研究 A 有全文，可以整理方法與限制；研究 B 僅有摘要，部分欄位待補；研究 C 的族群不同，不能直接合併解讀。

討論題可能是：「短期血糖指標改善，是否足以代表長期健康效益？」並標出需要進一步閱讀的段落。講師能建立可回查的教材，學員也能練習區分研究結果、推論與未解問題。

### 🐾 模擬案例三：寵物品牌 OMO 活動分析

品牌團隊想了解競品如何連接線上會員、門市體驗與後續回購。

**關鍵提示詞：**

> 請分析我提供的三家寵物品牌活動頁，整理活動期間、參加資格、優惠條件、線上操作、門市兌換及回購機制。標出缺漏與過期資訊，再提出三個適合小型團隊試行的活動構想。清楚區分競品公開事實與你的建議。

**模擬產出：** 一份活動比較表與三張試行提案：線上預約串接門市體驗、會員集點結合到店活動、首購後提供使用教學與回饋問卷。

每張提案列出步驟、人力與觀察指標。沒有公開成效數據，就不宣稱競品活動有效。團隊可以從資料出發做小規模實驗，再用自己的結果決定是否擴大。

### 🎯 好提示詞，讓交付標準更清楚

想讓同一套方法跨部門重用，可以在提示詞加上三個要求：每個重要結論保留證據、每個未知欄位說明原因、每份成果列出下一步。這些要求會讓報告更容易交接，也讓接手同仁知道哪些內容可以使用、哪些地方還需要補資料。

例如「幫我研究競品」的範圍太大，可以收斂為「比較三個指定活動頁的會員資格與兌換條件，輸出一張表，過期活動分開列示」。先把任務縮小，就比較容易看出工具是否取得正確資料，以及 Agent 是否理解比較基準。

實際執行前，也要確認來源是否允許存取。需要登入或付費的資料，不能因為工具具備擷取能力，就視為已取得使用權。資料進入系統後，網頁內的文字只作為研究材料，不能自行改變任務或要求執行額外操作。

### 📏 用成果驗收，而不是用文章長度驗收

第一輪可以抽查三筆資料：網址是否對應正確頁面？數字是否與原文一致？摘要是否省略重要條件？如果來源只寫「活動優惠」，報告就不能自行補成折扣幅度；如果規格缺少重量，也不能直接換算每公斤成本。

建立固定的驗收習慣後，企業才能逐步累積可重用流程。每次記錄任務、來源、版本與缺漏，下次就有改善依據；真正值得保存的，是經過核對的證據，以及人員如何運用證據做判斷。

### ✅ 先分清楚交付範圍

目前 v0.1.2 提供圖卡、整合指南、設定範例、工作流與驗收文件。客戶端連線尚未實測，自訂企業 MCP 伺服器尚未實作。排程監控、自動告警及知識庫寫入，需要另外串接與驗收。

官方 Agent Skill 可協助 Coding Agent 理解 API；企業任務仍需要清楚的規格。重用底層能力，把開發力氣放在資料品質與可交付成果。

最後，請問自己：如果這份報告會影響下一筆採購、下一堂課或下一次行銷決策，每個重要結論，是否都找得到依據？

從這個問題開始，AI to Agent 才會成為能累積的企業能力。
